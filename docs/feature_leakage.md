# データリーク防止の設計

本アプリは「富岳にジョブを投入する前」に成功確率を予測するためのものである。
したがって、モデルへの入力として使ってよいのは **ジョブが実際に実行される前
（投入時点）に値が確定している情報だけ** である。実行後にしか分からない情報
（実測の消費電力・flops・実行時間など）を混ぜると、モデルは「答えを見てから
答えを予測する」状態（データリーク）になり、オフライン評価の精度は不当に
高く見えるが、実運用（投入前の予測）では全く使い物にならなくなる。

この切り分けの実装は [`src/config.py`](../src/config.py) に集約されており、
本ドキュメントはその内容を人間が読みやすい形でまとめたものである。

## 使用した特徴量（投入時点で既知）

F-DATAの生カラムのうち、以下だけを安全な入力として使用している。

| 生カラム | 内容 | 派生した特徴量 |
|---|---|---|
| `nnumr` | 要求ノード数 | `nnumr_log`（log1p変換） |
| `elpl` | 要求経過時間上限（秒） | `elpl_hours`（時間に変換） |
| `nnumr` × `elpl` | （派生） | `node_hours_log`（要求ノード数×時間、総リソース量の目安、log1p変換） |
| `mszl` | 要求メモリ上限 | `mszl_specified`（明示指定したか0/1）, `mszl_gib_log`（指定時の値GiB、log1p変換） |
| `freq_req` | 要求動作周波数 | そのままカテゴリ変数として使用 |
| `adt` | 投入（到着）日時 | `submit_hour`（0-23時）, `submit_dow`（曜日） |

## 特徴量から除外した生カラム（実行後にしか分からない = リーク）

以下は実行後（ジョブ終了後）にしか値が確定しないため、**学習・推論の
どちらにおいても一切使用していない**。

| 生カラム | 内容 |
|---|---|
| `cnumat`, `cnumut`, `nnuma`, `nnumu` | 実際に割り当て/使用されたコア数・ノード数 |
| `qdt`, `schedsdt`, `deldt`, `sdt`, `edt` | スケジューリング・実行に関する各種タイムスタンプ（`adt`以外） |
| `idle_time_ave` | 実行中のアイドル時間（実測） |
| `perf1`〜`perf6` | 実行サイクル数・演算数などのハードウェアカウンタ（実測） |
| `econ`, `avgpcon`, `minpcon`, `maxpcon` | 消費電力（実測） |
| `msza`, `mmszu` | 実際に割り当て/使用されたメモリ量 |
| `uctmut`, `sctmut`, `usctmut` | 実測CPU時間 |
| `freq_alloc` | 実際に割り当てられた動作周波数 |
| `flops`, `mbwidth`, `opint` | 実測flops・メモリ帯域・演算強度 |
| `pclass` | 実行特性から事後的に分類された性能クラス |
| `duration` | 実際の実行時間（実測） |
| `ec` | ジョブ終了コード（ターゲット変数そのもの） |

## 投入時点で分かるが、あえて使わなかったカラム

以下は「投入時点で分かる」という条件自体は満たすが、リーク以外の理由で
特徴量から除外している。

| 生カラム | 除外理由 |
|---|---|
| `cnumr`（要求コア数） | `nnumr`（要求ノード数）とほぼ完全に比例（1ノード=48コア固定、標準偏差0）しており、情報量が重複するため |
| `pri`（優先度） | 5種類の値（127, 255, 250, 110, 100）が観測されるが、これが「ユーザーが投入時に指定する値」なのか「スケジューラが `qdt`〜`schedsdt` の間に動的に割り当てる値」なのかがデータセットのドキュメントだけでは判別できない。後者であれば投入前にユーザーが知り得ない値になる（＝リークになり得る）ため、安全側に倒して除外している |
| `jnam`（ジョブ名） | 投入時点で分かる情報だが自由記述文字列であり、人間がフォームに入力するには不向きなため |
| `embedding`（Sentence-BERT埋め込み） | 生成元・生成タイミングがデータセット側のドキュメントで明確にされておらず、投入前情報であることを確実に保証できないため、安全側に倒して除外 |
| `jid`（ジョブID） | 単なる識別子であり、それ自体に予測に有用な情報は含まれないため |

### `jobenv_req`（ジョブ実行環境）: 時間的に不安定なため除外

`jobenv_req`（キュー／リソースグループに相当、匿名化済み）は投入時点で
分かる情報だが、特徴量には含めていない。2021年4月〜2024年3月の約3年間は
ほぼ100%が同一カテゴリ（`jobenv_req_0`）で占められているのに対し、
2024年4月だけ突然ほぼ全てのジョブが別カテゴリ（`jobenv_req_1`）に
切り替わっている。周期的な季節変動ではなく、運用体制か資源配分の枠組みが
一度きり変わったことを示す変数だと考えられる。

学習データにはほとんど登場しないカテゴリがテスト期間（2024年3-4月）の
大部分を占めることになるため、この特徴量を含めて学習するとテストセットの
ROC-AUCが0.44（ランダムに劣る）まで悪化することを確認した。データリーク
ではなく、**時間的に不安定で未来の期間に汎化しない**という理由で除外して
いる。

### `usr`（投入ユーザー）: 匿名化IDが実際の利用者と対応しない

「そのユーザーの過去の成功率」は個人の傾向を強く反映する特徴量になり
得るが、本アプリでは `usr` を特徴量にもUI入力にも一切使用していない。

`usr` はF-DATA内で匿名化されたIDであり（`docs/feature_list_full.csv` の
`Anonymized: true`）、実際の富岳の利用者名（例: `u11111` のような形式）
には復元できない。この匿名化マッピングが月をまたいで一貫していること自体は
実データで確認できた（同一の匿名化IDが複数月にわたって同じジョブ名で
登場する）。しかし、この匿名化IDから実際のユーザー名への対応表は公開されて
いないため、実際の富岳利用者が本アプリに自分の本名義のユーザー名を入力
しても、学習データ内のどの `usr_XXX` とも一致しない。

概念としては、富岳センターが自前の内部利用実績データベースと連携すれば
「ユーザーの過去の成功率」という特徴量は実運用でも有効に機能し得る。
しかし公開データセットのみを使う本プロトタイプでは、実際の利用者が
恩恵を受けることが原理的にできない実運用上ほぼ意味のない特徴量になるため、
最初から特徴量・UIの両方に含めていない。

## モデルが使う情報について

上記の設計により、モデルが利用できるのは「ノード数」「経過時間上限」
「メモリ上限」「動作周波数」「投入時刻・曜日」という、実際にジョブを
投入する際にユーザー自身が指定する（あるいは把握している）情報だけに
限定されている。ユーザーの識別情報や、時期によって意味が変わってしまう
運用上の区分に依存していないため、評価結果は実際の投入前予測としての
妥当性を保っている。

その分、モデルが手がかりにできる情報は限られており、失敗の主要因が
個々のジョブ設定よりも実行内容（コードのバグや設定ミスなど、データセット
に含まれない情報）に依存している場合、予測性能には自ずと限界がある。
実際の評価指標は [`training_report.md`](training_report.md) を参照。

## 時系列を考慮したtrain/val/test分割

- **train**: 2021年4月〜2023年12月（33ファイル）
- **val**: 2024年1月・2月
- **test**: 2024年3月・4月

train・val・testは完全に別の期間であり、val・testはtrainより時系列的に
未来にあたる。これにより、ランダムシャッフルによる分割では見えにくい
「未来のデータに対する汎化性能」を評価できる。
